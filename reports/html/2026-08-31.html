#1 Resolve 复杂粗剪交接：AI Shot Mapping → 多轨/正反变速 OTIO → DRT → Resolve 实际渲染验收 · 99

核心判断：8 月 31 日连续三组 live proof 把离线 conform 从简单单轨硬切推进到真正有生产价值的几何：V2+ 多视频轨可叠加、正向 constant-speed retime 可写入、倒放也可写入，而且都经过 Resolve 导入、readback 与真实 render 验证。最关键的不是“又多三个 API”，而是 AI Shot Mapping 现在有机会把镜头层级、B-roll 叠层、慢放/快放/倒放直接交成 Resolve 可继续编辑的时间线，而不是只输出 JSON 后再人工重建。

解决的问题：解决 AI 粗剪在复杂时间线上的最后一公里：模型能决定镜头，但多轨 B-roll、速度变化和倒放仍需要人工在 Resolve 里重搭，导致自动化只能停留在简单硬切。

主流方案对比：直接让 MCP 在线逐条改 Resolve 最直观，但连接状态、版本差异和大量原子写入会增加失败面；只导 EDL 又会丢多轨和 retime。先生成受约束 OTIO/assemble spec，再离线 author DRT、导入 Resolve 并做 readback/render，是更可回退、也更适合批量验证的中间方案。

今天可以做：用一个 15–30 秒测试序列做 5 个镜头：V1 主线 3 段、V2 B-roll 2 段，其中 1 段 50% 慢放、1 段倒放。由现有 Shot Mapping 生成对应 OTIO/assemble spec，导出 DRT 后进 Resolve；只检查四件事：轨道位置、源范围、速度方向、最终渲染帧数是否全部正确。

后续机会：如果同一测试能连续 3 次无人工修复导入并渲染正确，就把“AI_analysis/Shot Mapping → OTIO/DRT”升级为粗剪主出口；如果 retime 或 V2 仍有版本差异，就只自动 hard cut + multi-track，把速度效果保留为人工标记。

#2 高级感口播包装：成片口播 → AI 生成动态图形覆盖层 → 确定性 MP4 → 回 Resolve/剪映精剪 · 98

核心判断：HyperFrames 刚开源的价值不在于再做一个 AI 视频编辑器，而是它明确提供 talking-head-recut、embedded-captions、motion-graphics 等 Agent workflow，把 HTML/CSS/GSAP 动画渲染为确定性 MP4。对现有 DaVinci/剪映主链，最低成本用法是把它限定成“高级包装素材生成器”：让 Agent 根据口播文稿和时间点生成 lower-third、数据卡、关键词动效、侧栏、PiP 或透明/独立覆盖层，再回主时间线人工决定是否采用。

解决的问题：解决高级感口播里最耗时间、又高度重复的包装工作：字幕以外的数据卡、金句、动态图形、标题、侧栏和 PiP 往往需要手工搭动画，但又不值得为了这些元素迁移到另一个完整编辑器。

主流方案对比：直接在 Resolve Fusion/剪映里手做自由度最高但耗时；Remotion/AE 模板自动化能力强但需要维护 React/AE 工程。HyperFrames 用普通 HTML 作为 source of truth，并提供 lint、snapshot、preview、render 和专门的 talking-head workflow，更适合先做单个包装镜头的小成本验证。

今天可以做：从一条现有正面口播里截 20 秒，只选 3 个包装点：开头标题、一个数据/事实卡、一个关键词金句。不要让它重剪原片，只生成 3 个可独立叠加的 MP4/透明素材；回 Resolve 对齐原时码，比较手工制作时间与实际视觉质量。

后续机会：如果 3 个包装点里至少 2 个无需重做即可入片，就沉淀一套固定 frame.md/品牌规范，把“文稿标记 → 包装素材”变成口播剪辑前置工序；如果视觉仍像模板或改稿成本高，就只保留标题/数据卡两类确定性元素。

#4 H3 缺镜头返修：真实前镜+音频/多参考 → 2–5 秒续接 → FFV1 无损中间件 → Resolve 入片验收 · 95

核心判断：8 月 31 日该 fork 连续修复 FFV1 output 和 AV source loading，前一轮又加入 lossless FFV1 final output。结合已有 multi-reference、AV extension、timeline audio、latent masking，最值得利用的是“生成完成后不再先压成有损交付文件”，而是用无损中间件回 Resolve 判断连续性、色彩和二次处理空间。它把 AI 生成从 demo 输出推进到更接近 NLE 素材的返修链。

解决的问题：解决 AI 补镜头即使内容可用，也可能在二次压缩、音画参考加载或多段延长时损失质量/连续性，导致回 Resolve 后无法自然调色、裁切和再次编码。

主流方案对比：直接输出 H.264 最省空间，适合预览；但用于最终入片会叠加压缩损失。整段重新生成又浪费已经正确的内容。只补短区间并用 FFV1 无损中间文件进入 NLE，磁盘更大，但验证阶段成本可控。

今天可以做：选 1 个真实 2–5 秒缺口，输入前镜尾段和需要的音频/人物参考，最多生成 3 个候选；最终候选统一输出 FFV1，再进 Resolve 做一次正常调色/缩放/二次 H.264 导出，检查接缝、音画连续性和二压差异。

后续机会：只有当无损中间件明显改善二次处理质量且至少 1/3 候选真正入片，才把它加入缺镜头分支；否则继续用低成本预览编码，不增加磁盘和流程复杂度。

#5 剪映草稿写入安全门：精确检测 CapCut/剪映进程 → 关闭后再写 → lint/实开验收 · 92

核心判断：8 月 30 日 capcut-cli 修复了编辑器进程检测逻辑：不再把整个进程列表拼起来做 substring 匹配，而是逐个精确比较进程名。这个改动本身不炫，但它对应一个直接的生产风险——自动脚本如果误判编辑器未运行，可能在 CapCut/剪映仍打开时写草稿；误判已运行则会无意义阻塞。今天的价值是把“编辑器必须关闭”做成确定性写入门禁，而不是继续增加批量功能。

解决的问题：解决批量写草稿前的并发风险和误判：编辑器正在读写同一草稿时，外部 CLI 再修改文件可能造成覆盖、缓存不同步或无法复现的问题。

主流方案对比：人工记得先关剪映最简单，但自动批量流程无法依赖记忆；直接强杀进程风险又太高。精确检测 → 明确提示关闭 → 写入 → lint → 人工打开，是最低成本的安全门。

今天可以做：准备 1 个测试草稿：剪映开启时执行一次写入命令，确认必须被阻断；关闭剪映后再执行，确认写入成功；随后跑 lint 并实际打开草稿。不要测试更多效果功能。

后续机会：若门禁稳定，就把它固定在所有批量草稿写入前；若 macOS 中文版进程名仍有差异，只补进程名映射，不扩展成复杂进程管理器。
