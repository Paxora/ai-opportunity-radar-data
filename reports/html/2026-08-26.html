#1 OpenChatCut 直播拆条：长直播 → 多模态证据账本 → 多条独立短视频 → 人工验收 · 99

核心判断：2026-08-25 的 livestream-to-clips 工作流先建立 stream map，再用语音、画面、音频、互动和元数据生成候选，先做硬性拒绝门禁，再评分和去重；随后新增多序列独立导出、来源区间 provenance、后台进度和可选保存到 My Media，并记录真实浏览器 Agent 运行验证。价值是把长直播找高光从黑盒摘要变成可追溯的批量交付。

解决的问题：解决直播、访谈、长口播素材需要人工从头看片找高光，且模型只看转录容易错过视觉反应、音乐峰值、产品演示和上下文的问题。

主流方案对比：常见 AI clipping 工具直接给自动高光，速度快但选择理由和上下文边界不透明；OpenChatCut 成本高一些，但每个候选保留 source range、证据、缺失证据与风险标记，并要求最终看时间线帧，不把工具成功当成成片成功。

今天可以做：只用一段 20–40 分钟真实长素材做测试，生成 3 条 30–60 秒候选；检查每条是否都有 setup/peak/payoff、来源时间码和至少两类证据；先只导出最高分一条人工验收。

后续机会：记录人工最终保留率、每条人工修剪时间和重复候选率；若 3 次测试中候选保留率稳定超过 50%，再接到现有 DaVinci/剪映精剪流程。

#2 Resolve 实测响度粗混：对白/音乐 → dry-run 增益计划 → 实际渲染复测 → 再决定是否采用 · 97

核心判断：Resolve MCP 的 mix_plan 先根据对白建立增益和音乐 ducking，再实际渲染 premix、重新测 EBU R128，并返回 achieved LUFS、true peak、LRA 和目标差值；后续又修复了 ebur128 解析可能误读单帧进度行的问题。价值是不再相信理论增益，而是用真实输出验收。

解决的问题：解决 vlog/口播批量剪辑中对白和音乐响度靠经验手调、不同视频结果波动，以及自动增益看似正确但最终 true peak 或综合响度仍不合格的问题。

主流方案对比：传统 Normalize 或固定压低 BGM 最简单，但只处理单一指标；完整 Fairlight 自动混音工程又过重。这个方案只做 gain staging、music bed 和 ducking，并默认 dry-run，适合作为低风险第一层自动化。

今天可以做：取一条已完成的 45–60 秒口播/探店视频，分出对白与 BGM 两轨，先只运行 dry-run；再在副本上应用一次，比较处理前后 integrated LUFS、true peak 和对白清晰度。

后续机会：若连续 3 条视频都能拉进目标区间且人工只需微调音乐电平，就把 rough mix 设成时间线交付前固定预检。

#5 capcut-cli 品牌字幕往返：剪映草稿 → Styled ASS → 外部修改 → 回到可编辑草稿 → lint 验收 · 92

核心判断：v0.20.0 已支持把剪映字幕的字体大小、颜色、透明度、粗斜体、下划线、对齐、边框/阴影、局部 range 样式以及 karaoke timing 导出为 ASS，并在导回时恢复局部 bold/italic/color/size 样式。价值是让品牌字幕经过外部批处理后仍回到可编辑草稿。
