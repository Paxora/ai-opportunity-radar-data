#1 Resolve MCP 2.98：控制面板令牌化 → 回环绑定 → 再开放正式项目写权限 · 99

核心判断：8月18日 v2.98.0 修复了一个直接影响正式剪辑安全边界的问题：控制面板此前存在未鉴权状态接口、缺少 Host/Origin 校验，并允许把面板绑定到 0.0.0.0；组合后，浏览器页面可能拿到网络传输 token 并控制 MCP 工具。新版改成每次启动独立 bearer token、只允许 loopback、Host/Origin/Content-Type 全部门禁，并把状态文件迁到私有目录。

解决的问题：解决“本地 MCP = 天然安全”的错误假设，避免打开任意网页时，浏览器侧请求间接获得 Resolve 控制能力；也避免 AI 自己把控制面板暴露到非本机地址。

主流方案对比：很多本地自动化只强调 localhost，却没有处理 DNS rebinding、CSRF、token 泄漏和可配置 bind address。v2.98 把这些风险具体封闭，比继续增加剪辑工具数量更值得先升级。

今天可以做：先只在测试项目升级到 v2.98.0：验证裸 http://127.0.0.1:8765 被锁定、带 #token 的完整 URL 可进入、host=0.0.0.0 被拒绝，再执行 1 次只读 timeline 查询和 1 次可回退写操作。全部通过后再用于正式项目。

后续机会：若安全门禁稳定，就把“版本 >=2.98 + loopback-only + token URL”加入 Resolve MCP 开工前检查；正式素材仍保留逐工具审批，不因为控制面板加固就放宽写权限。

#2 小红书只读 MCP：公开笔记/评论 → 证据卡 → 人工选题，不开放发布权限 · 98

核心判断：该项目把小红书/RedNote 能力主动压缩为 6 个只读工具：登录检查、首页、搜索、笔记详情/评论、用户主页；明确禁止发帖、评论、点赞、收藏等写操作，同时限制操作频率、评论读取规模，并返回无访问 token 的 sourceUrl。对案例研究来说，这是比“全功能自动运营 MCP”更合适的最小权限方案。

解决的问题：解决为了搜索案例和读评论，却被迫把账号发布/互动权限一起交给 Agent 的问题；同时保留原始页面链接，方便人工回查证据。

主流方案对比：全功能小红书 MCP 功能更强，但研究任务并不需要发布权；手工浏览安全但检索和整理成本高。只读 MCP 在二者之间提供了更低权限、可引用、可结构化处理的研究层。

今天可以做：用专门测试账号只搜索 1 个你近期准备拍的主题，读取 10 条公开笔记和每条前若干评论，生成“Hook/用户痛点/场景/可迁移点/原始链接”五字段证据卡；不做批量采集，不开启任何发布链路。

后续机会：若一周内证据卡能稳定提高选题判断效率，就把它固定成 Snow 选题前置研究工具；如果仍需大量人工回查，保留浏览器手工方式，不继续开发自动发布。

#3 OpenBiliClaw：逐来源增量同步 + LLM 预算门禁 → 低成本维持案例池 · 96

核心判断：8月18日新增 per-source incremental sync，两级开关要求 scheduler 总开关与单一来源开关同时开启；同一批更新还加入后台 LLM 每小时调用预算和 embedding 连续失败熔断。价值在于只让真正需要的来源周期回拉，避免浏览器无意义打开平台页和后台模型额度持续消耗。

解决的问题：解决跨平台候选池常见的两个隐形成本：所有来源一起周期同步造成平台风控/浏览器打扰，以及后台发现任务在无人值守时持续烧 LLM/embedding 额度。

主流方案对比：普通聚合工具通常只有“全开/全关”或固定 cron；这里可以按 XHS、抖音、YouTube 等分别控制增量，并设置 LLM 预算和熔断，更适合先小规模验证高信号来源。

今天可以做：只开启 YouTube 与小红书两个已经证明有用的来源增量同步，其余保持关闭；把后台 LLM 预算设为保守上限，运行一个周期后只看新增候选数、有效候选率和模型调用量，不调推荐算法。

后续机会：若单来源增量的有效候选率明显高于全量 discovery，就把来源预算按“有效候选/调用成本”动态分配；否则退回手动触发，不做常驻后台。

#4 CapCut Mate：远程素材断点续传 → 草稿生成 → 人工打开验收 · 94

核心判断：CapCut Mate 已提供完整草稿、视频/音频/字幕/关键帧等 API；8月18日连续重构远程素材下载，加入断点续传并提高重试容错。真正的机会不是“多一个剪映 API”，而是让 AI 生成草稿时远程大素材不必因单次网络失败整段重下。

解决的问题：解决 n8n/Coze/本地 Agent 用 URL 素材批量生成剪映草稿时，大文件下载失败导致整条工作流报废或重复传输的问题。

主流方案对比：capcut-cli 更适合本地、确定性的草稿修改与 lint；CapCut Mate 更偏 API/工作流编排和远程素材。今天只验证它在远程素材链路的可靠性，不取代现有本地 lint 门禁。

今天可以做：拿 1 个 300MB 以上测试视频，通过 API 建一个 15–20 秒竖屏草稿；下载中途主动制造一次网络中断，确认恢复后不是从 0 重新下载，并最终能在剪映打开。只做测试草稿，不接正式账号发布。

后续机会：若断点续传和草稿打开连续通过 3 次，可把它作为“云端/远程素材 → 初始剪映草稿”入口；最终交付前仍交给本地剪映或 capcut-cli 做 lint 和人工验收。

#5 ComfyUI MiniMax-H3：局部 video/audio mask → 失败区段重做 → 入片率验收 · 91

核心判断：8月18日 ComfyUI 为 MiniMax-H3 增加 per-token video/audio latent noise masks，并加入 prompt embeddings 支持。价值不在模型又多两个参数，而是更接近“只对失败区段施加生成/重做约束”，减少整段视频和音频全部重跑。

解决的问题：解决生成镜头只有局部动作、画面或声音失败时，整段重新生成带来的成本和随机漂移；尤其适合已经基本可用、只差 1–2 个局部区段的短镜头。

主流方案对比：传统 I2V/T2V 常把整段作为一次生成单位；局部 mask 给了更细的控制入口，但是否真的降低返工仍需真实时间线验证，不能只看节点能力。

今天可以做：找 1 个已有生成镜头，人工标出一个明确失败区段，只对该区段做 mask 重跑；与整段重生成各做一次，比较人物一致性、音画连续性、耗时/成本和是否愿意入片。

后续机会：只有局部重做在至少 3 个真实镜头里同时降低成本且提高入片率，才纳入缺镜头工作流；否则保留简单整段生成，不为高级控制增加复杂度。
