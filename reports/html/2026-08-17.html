#1 capcut-cli：多段字幕样式 → UTF-16 正确索引 → lint 修旧稿 → 剪映人工验收 · 99

核心判断：8月16日修复了一个会直接影响批量字幕质量的底层错误：styles[].range 应按 UTF-16 code units 保存，而不是 UTF-16LE bytes。此前全段样式可能表面正常，但 karaoke、关键词高亮、多段样式会出现偏移或完全不生效。新增 lint text-range-doubled 可识别并修复旧稿。

解决的问题：解决 AI 批量生成剪映草稿时，字幕关键词高亮、逐词 karaoke、局部强调在脚本层显示成功，但打开剪映后样式错位或消失的问题。

主流方案对比：普通草稿脚本往往只检查 JSON 能否写入；这个修复来自对 38 个 App 原生草稿、211 个 text materials 的实测，并把读写、preset、lint、SRT 导出统一到同一索引语义，验证强度明显更高。

今天可以做：拿一个包含中文+emoji+英文关键词的 20 秒测试草稿，做三段不同样式和 karaoke；先跑 lint，再打开剪映核对高亮位置。若有旧草稿，先用 lint --fix 修复一份副本，不直接批量改正式项目。

后续机会：如果连续 3 个真实草稿的多段样式都能稳定回读，就把 text-range lint 固定为所有批量字幕写入后的门禁；否则暂时只保留单段样式。

#3 XhsGrowthAgent：扫码登录 → 创作者页证据确认 → 只读研究 → 再生成选题卡 · 95

核心判断：8月16日修复了 raw-CDP 登录状态的误判：不再只依赖 creator cookie，而是在缺少强 cookie 时进入创作者主页，用页面证据确认真实登录状态。对内容研究链的价值是减少“实际已登录但系统持续判定掉线”造成的采集中断。

解决的问题：解决小红书研究自动化中扫码成功、创作者后台实际可用，但状态机仍显示 logged-out/www_only，导致后续搜索、读取和分析链无法继续的问题。

主流方案对比：单纯 cookie 判定实现简单，但平台 cookie 策略变化就容易失效；页面证据确认更接近真实可用状态。代价是多一次页面访问，因此只值得用于状态确认，不应扩展成无人值守发布。

今天可以做：用一个研究账号登录后只做搜索和读取；分别记录 cookie 状态与 creator_page_ready 状态，确认二者不一致时页面证据是否能正确恢复研究链。今天不启用自动发布。

#4 OpenBiliClaw：候选池后台 hydration 隔离 → 不吞前台候选 → 人工选题 · 93

解决的问题：解决跨平台候选已经搜到，但桌面端后台 hydration 在展示前消耗 pool，导致人工真正看到的可选案例减少、候选数量与预期不一致的问题。

主流方案对比：传统推荐前端常把加载和消费混在一起；把 hydration 与 pool consumption 分离后，更容易保证研究阶段的候选完整性。但这仍只是候选层修复，不能替代人工价值判断。

今天可以做：固定同一关键词跑两次 20 条候选，一次开启桌面后台 hydration、一次关闭；比较最终可见候选数量、重复率和证据链接完整率。只有数量稳定且质量不下降才保留。
