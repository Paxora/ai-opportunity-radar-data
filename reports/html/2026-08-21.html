#1 capcut-cli：渲染前能力探测 → 缺失 filter 直接失败 → 再进入批量成片 · 99

核心判断：8月20日的新修复把 fps、scale、pad、setsar、format、concat、trim、setpts 这 8 个基础 filter 也纳入 ffmpeg capability probe。此前只检查 drawtext/overlay/libx264，导致某些精简 ffmpeg 在真正渲染时才报原始 parser error。真正的价值是把“机器上的 ffmpeg 到底能不能完成这份草稿”提前变成明确门禁。

解决的问题：解决批量草稿已经生成、进入正式 render 后才因 ffmpeg 缺基础 filter 整批失败的问题；尤其适合不同机器、打包版 ffmpeg 或远程执行环境。

主流方案对比：多数脚本默认系统 ffmpeg 能力完整，失败后才看 stderr；capcut-cli 现在把基础链路提前探测，更适合批量生产，因为失败点从“渲染中途”前移到“开工前”。

今天可以做：用当前 Mac 上实际调用的 ffmpeg 跑一次 capability probe，再用一份 20 秒草稿执行 dry-run 和正式 render。若缺 filter，先解决 ffmpeg 环境，不要继续改草稿或模板。

后续机会：通过后把 capability probe 固定成每台机器/每次环境升级后的开工检查；批量任务只在 probe 全绿后进入渲染队列，减少整批返工。

#2 Resolve MCP：Fusion 关键帧删除 → 操作后回读 → 只接受真实生效的自动修改 · 98

核心判断：8月20日修复确认 fusion_comp 的 delete_keyframe 自 v2.1.0 起实际上从未正确工作：旧实现对 Input 调用不存在的 RemoveKeyFrame。新实现改为找到 BezierSpline 后调用 DeleteKeyFrames，并且不相信返回值，而是重新读取 keyframe 列表确认是否真的删除。价值在于再次证明 Resolve/Fusion 自动化不能把“API 调用没报错”当成功。

解决的问题：解决自动修改关键帧时出现“工具返回成功或异常不清楚，但时间线实际没变”的假成功问题，避免 Agent 在错误状态上继续后续编辑。

主流方案对比：普通自动化只看函数返回值或无异常；这次修复明确发现 DeleteKeyFrames 即使成功也可能返回 None，因此必须用状态回读证明结果，更符合正式剪辑的可靠性要求。

今天可以做：在测试时间线做一个最小闭环：给一个 Fusion 参数加关键帧 → 读取确认存在 → 删除 → 再读取确认消失。不要先迁移正式项目，先验证当前 Resolve 21 环境中的真实行为。

后续机会：把“写操作后回读”推广到 transform、keyframe、marker、clip range 等关键动作；任何不能被回读证明的动作只允许停留在测试时间线。

#3 OpenBiliClaw：去掉假负反馈 → 只用真实交互训练偏好 → 选题池不被误伤 · 97

核心判断：8月20日修复了两类会污染偏好数据的假信号：程序化 seek 被误当成用户主动拖动；视频卡片长文本里只要出现“不感兴趣”等词就可能被误记为 dislike。现在 seek 只在真实指针/键盘交互后记录，负反馈也只识别短控制标签。价值是让“用户行为 → 偏好 → 候选筛选”这条链少吃脏数据。

解决的问题：解决推荐/选题系统因为浏览器自身恢复进度、页面文案关键词而错误判断用户厌恶某类内容，导致真正有价值的候选被持续压低。

主流方案对比：普通跨平台采集常把 DOM 事件直接当行为事实；这里加入真实交互条件和控件语义约束，虽然少收一些事件，但数据可信度更高，更适合做长期选题画像。

今天可以做：先不调推荐模型。回放 20 条近期行为日志，重点检查 seek/dislike 是否能解释为真实人工动作；把明显误判的旧事件标记出来，再观察候选池变化。

后续机会：如果误反馈显著减少，就把“可解释行为事件率”作为画像质量指标；只有来源、动作和上下文都能解释的事件才进入长期偏好层。

#4 小红书 MCP：研究与发布权限拆开 → 先做只读案例卡 → 人工批准后再发布 · 94

核心判断：今天没有发现足够强的新小红书项目值得替换现有成熟链路，因此不为了上新而换工具。现有 xiaohongshu-mcp 已覆盖搜索、详情、登录和发布，并明确提供更低部署成本的 x-mcp 浏览器插件。真正有价值的方案仍是把研究和发布拆开：日常只读搜案例，发布留给人工确认。

解决的问题：解决内容研究工具为了方便把发布、互动、登录等高权限能力一起交给 Agent 的风险，同时避免为少量案例检索维护复杂 Docker 环境。

主流方案对比：全权限运营 MCP 功能更多，但权限边界更宽；浏览器侧/只读研究链牺牲无人值守自动化，换来部署更轻、风险更低，当前更符合真实账号运营阶段。

今天可以做：只验证搜索 → 笔记详情 → 原链接回看这三步，用 10 条候选生成“Hook/结构/可复刻点/不适配原因”案例卡；不要启用自动点赞、评论或发布。

#5 ComfyUI：视频输出先统一 HDR/编码 → 再进入剪辑验收 → 避免生成后交付返工 · 92

核心判断：8月20–21日 Save Video 节点连续加入 HDR 视频保存、AV1、mkv/webm，以及 H.264 的 HDR color space 选项。真正的机会不是“支持更多编码”，而是把生成镜头的输出规格前置到工作流末端，减少进入 Resolve/剪映后才发现色彩空间或封装不合适而重导。

解决的问题：解决 AI 视频生成完成后，在交付到剪辑软件阶段才发现编码、容器或 HDR 色彩空间不匹配，造成二次转码、色彩偏差或批量返工。

主流方案对比：常见 ComfyUI 工作流只关心生成成功，最后用默认编码保存；新的 Save Video 能把交付规格显式化，更接近真正生产链，但仍需要在目标剪辑软件里验证。

今天可以做：用同一 5 秒生成镜头输出两份：常规 H.264 和目标 HDR/H.264 配置；直接导入 Resolve 测试色彩、播放和导出，不做额外后处理。若 HDR 没有真实需求，就继续 SDR，不为新能力增加复杂度。

后续机会：若后续确实存在 HDR/高质量交付需求，再把编码/色彩空间做成项目级模板；否则保留单一 SDR 输出，优先稳定和兼容。
